# Pi TUI design language

Read this before editing a module the map below marks **TUI**. A rule is rewritten in place to its current state,
keeping its *why*; history is `git log -p docs/pi-design.md`.

Module map (`private_dot_pi/agent/workflow/*.mjs`), one responsibility each:

- `index` (TUI): the extension entry — config, broker connection, managed tool registration and gating, modes and commands, and wiring the other modules into pi's session lifecycle.
- `editor` (TUI): the composer — `CaretEditor`'s rule 5 shape, shell-mode prefix and fleet entry, and Tab argument completion.
- `plugin-api` (TUI): what plugins see of the extension API — the registration Proxy (renderers, `subagent` schema and description, quiet notices, the control-notice row, MCP tool identity) and the MCP server configuration handed to pi's MCP factory.
- `skill-display` (TUI): a sent skill invocation shown as its `/skill:` command (rule 5).
- `pending-input` (TUI): native queued steer/follow-up input, its rule 5 blocks and interrupt-and-send action.
- `rows` (TUI): the transcript's row grammar, the activity-group fold engine and the reasoning hide (rules 1, 2, 8), and the shared glyph/row kit the other TUI modules import.
- `shell` (TUI): the owned `!` block — runner, context delivery and its transcript block.
- `footer` (TUI): the status line, the working row and usage segments (rule 3).
- `header` (TUI): the session header.
- `usage` (TUI): the `/usage` entry — plan limits, context breakdown and session cost including subagents.
- `fleet` (TUI): the fleet rows and detached-run lifecycle (rules 4, 6).
- `peek` (TUI): the fleet peek dialog (rule 6).
- `replay` (TUI): a child's `events.jsonl` replayed into rule 2 rows for the peek.
- `dialog` (TUI): the shared dialog frame (rule 11).
- `questionnaire` (TUI): `ask_user_question`, its tool and dialog.
- `plan-approval` (TUI): the branch's revisioned plan, `submit_plan`, its decision and plan-view dialog.
- `web-fetch`: `web_fetch` — one public page fetched in-process behind its address guard, converted to markdown and answered by the search-tier model.
- `approval`: reviewing one action — classifier verdict or user confirm.
- `broker`: the policy broker — socket server, epochs and child leases.
- `children`: subagent launch validation and schema narrowing.
- `policy`: tool, path and mode policy.
- `operations`: the host side of a sandboxed tool worker.
- `ops-worker`: the sandboxed worker process that runs one tool's operations.
- `sandbox-runner`: launching a process inside srt with a leased environment.
- `tasks`: background shell tasks.
- `lines`: newline-delimited JSON framing.
- Each module has the one responsibility its map line states; a new concern gets its own module, or joins the module whose line names it, and the map line lands with it. *Why:* `index` had collected the composer, the plugin Proxy and the skill patch beside the workflow entry, so a TUI rule change meant reading an 800-line file for the 200 lines it touched.

The intent, from a side-by-side of pi and Claude Code: Claude Code's presentation of the work in progress, pi's own glyphs. Each rule carries the why that earned it.

1. **Transcript = Claude Code's shape, pi's glyphs.** `•` rows coloured by state for every row (tool calls, subagent launches and actions, child completion lines), `○` only on a fleet row, `↳` for the line under a row and for a group's member line (rule 2), `π` for anything the harness says in its own voice (turn line), `❭` as the one selection cursor (fleet, dialogs), `✔` for a chosen answer and the submit tab (rule 11), `☐`/`☑` for an unanswered/answered question tab (rule 11), `❯` for the prompt and for the message it sent (rule 5), `!` for the shell-mode prompt and the sent shell command (rule 5), `▸`/`▾` for a fold handle's state (rule 2). No `⏺`/`✻`/`◯` (Claude's signatures), no `Called`/`Explored` headers. *Why:* a borrowed signature reads as a clone; a glyph set that is ours reads as pi.
2. **Quiet while working.** Reasoning renders as nothing and takes no space: no lines, no click region (ctrl+t is moot) and no pi spacer, so the gap above a reply is one line from its first token, on every provider; the message, and so model context, keeps it (`docs/pi-coupling.md`, Hidden reasoning).
   - A tool row is its title and one `↳` summary line (`+12 −4`, the counts in the theme's own success/error pair, `4 matches`, `31 lines`, `no output`), never output. A failed shell command shows its first two and last two lines with `… N more lines` between and the exit status last; other errors show in full. A shell row that ran outside the sandbox (Claude Code's `dangerouslyDisableSandbox`) carries `· unsandboxed` on its title, background launch row included — the classifier may allow the escalation without a dialog. The plan row takes the tool's own `Plan approval` label, `Read plan` for a read. Image results fold as text results do; managed `terminal.showImages: false` suppresses native inline previews, not model image input.
   - The rows between two things that stay visible — successful workspace/MCP calls, web searches and fetches, tool and agent discovery (`tool_search`, subagent list), launches, subagent management calls (steer, status, interrupt, stop), background-task management (`workspace_task` output, stop, list) and `completed` child/task lines — are one group: a sentence that counts them ("Read 3 files, ran 9 shell commands (1 unsandboxed), launched 3 agents", `steered 1 agent`, `checked on 2 background tasks`); an escalated shell call stays a member and its clause counts it, so the sealed sentence still says the sandbox was left. While the group is the newest thing in the transcript it lists its members under a `•` sentence, one `↳` line per row in the row's own words (`↳ Ran npm test · 31 lines`, `↳ researcher › title`); once anything visible lands after it, it closes to the sentence alone, dim, behind `▸`. One row is not a group. A row still running is a plain row below the group and joins it when it succeeds. *Why:* the reader needs the list while it is happening and the count once it has passed; one rule for every class of row leaves nothing to remember per tool. Launches join because the fleet holds the running child (rule 6) and the completion line names agent and title (rule 4); a steer between two reads split the group for a row that says nothing its completion line does not.
   - Whatever stays visible closes the group: assistant text and pi's red lines under a reply (a truncation tail; an error or abort's tail, or its red tool rows), a `bg_wait` row (a blocking wait whose own sentence is the information), the Plan approval row, other plugin rows, a failed row (never a member), an unsuccessful completion, the turn line, a π note, a questionnaire's answers, a displayed plugin message or entry, the compaction summary, and user input — at once on submission (typed, queued steer/follow-up, or a `!` command), and again wherever a user box lands, whatever its source. What draws nothing closes nothing: a run's start, the question row itself, a quiet notice. *Why:* a run a quiet completion starts split one stretch of reads into two sealed groups with nothing visible between them.
   - A click on the handle moves the one group between sentence and members (`▸`/`▾`); the caret and an undimmed handle carry the open state, with no `· ctrl+o to expand` hint. ctrl+o toggles every group's rows in full and is the only way to tool output — while it is on, a click has nothing to change; the `!` block's output is the one output shown without it, because the user asked for it (rule 5). *Residual:* pi's own `Tool output: expanded` line is unreachable.
   - Group extent is derived from `rows.mjs`'s ordered timeline of facts — a maximal stretch of settled successful rows with a separator on its right, keyed by that boundary so ctrl+o and click state survive. *Why:* close triggers kept at call sites were forgotten (six had to remember, four did not). A displayed message pi appends outside the agent stream reaches no extension event, so `plugin-api.mjs` closes for it at the send, or after pi's deferred flush; a completion that lands while a reply streams folds above it, where pi mounts it; a compaction drops the facts of entries it cut, so a straddling group's first kept member draws the sentence. *Residual:* pi's and MCP's `ctx.ui.notify` lines, a send that bypasses the plugin Proxy, a /tree rebuild and a compaction an extension commits as a boundary draft (no `session_compact`) register no boundary.
   - *Why:* per-step reasoning summaries and head/tail previews were the "too verbose" the owner named; what was done stays a keystroke away.
3. **One place per fact.** Elapsed time rides the working spinner while the turn runs (`⠋ Interpolating… 1m 12s`) and the `π` turn line once it ends; the status line carries model · context · usage windows · branch on the left and live background shells · mode · approval on the right (`2 shells · execute · auto`), nothing transient; the expand state stays off it. *Why:* the clock on the status line duplicated the spinner two rows above it.
   - Plan limits consume Codex response headers and raw rate-limit events immediately into one snapshot; fresh native limits suppress automatic GETs for a minute. The GET fallback runs on footer attach, assistant/tool-result message completion and run end, at most once per minute automatically; skipped triggers are not queued and idle countdown ticks only render. `/usage` forces a fresh read through the same in-flight request; a newer native snapshot outranks that request in both footer and report. Otherwise failed reads report unavailable while the footer keeps its last good limits.
   - `/usage` is the on-demand detail behind the status line's `ses/wk %` and context: three `π` blocks — Plan (one bar per ChatGPT window with its reset spelled out; one dim `π Plan · unavailable` line without a codex login), Context (one bar, then system prompt, tools, project context, skills, messages and free, pi's real count as the headline, `~` when only estimates exist) and Cost (main, one line per model when there were several, and subagents from pi-subagents' versioned `cost` report, `(n unavailable)` for async children it could not resolve, and `unavailable` with no report). One colour for used (`accent`, `warning` from 90% on a plan window) — rule 12 keeps the outcome pair for outcomes; each row's tail names its top three contributors, never a full list, except Project context, which names every loaded file; Claude Code's durations, code-change counts and grid glyph are left out. *Why:* the owner wanted `/context` + `/cost` in one command with only the parts that change a decision, and pi's `/session` misses children, which the plugin's report covers.
4. **A turn ends when nothing is running.** The turn line prints at `agent_settled` only when no background child or task is live; with either running it waits for the follow-up run to settle (or the user to type) and then prints the total. Meanwhile the working row shows a frozen `π <verb> for <duration>` snapshot instead of a spinner; a child wake reuses that row and only the final settle appends a turn entry, so root inactivity is visible without a transcript milestone for every staggered completion. An aborted run prints `π Interrupted after …` at once. *Why:* pi's `agent_settled` is honest about the root run, not about the work; printing "done" while a child still ran was the complaint.
   - Background shell tasks are running work like children (`• Started cmd in background`, `↳ task t1 · running`); the in-progress bullet stays static.
   - Each async child that ends prints `• agent finished · title · 2m 14s` (the run's own `durationMs`, launch to end), or its status word (`failed`/`stopped` in the error colour, `paused`/`partial`/`detached` in the warning colour); a background task ends the same way, `• task t1 finished · command · 12s`. `completed` lines join rule 2's group; other statuses stay visible and resumed rows stay ungrouped. *Why:* separate completion milestones fragmented activity.
   - pi-subagents' control notice takes the same line (`• researcher needs attention · …`), composed over the plugin's renderer. Its completion notice does not draw; workflow child notices and the result-write failure take the same status line, a watchdog clarification a `π` line, with their text two in. Content is untouched.
5. **Composer = the user box, and the user box = the composer.** A shaded block in pi's `userMessageBg`: one blank shaded row above and below the content, `❯` at column 0 on the first content line, no rule lines, no placeholder; the status line follows the bottom row directly. A sent message carries the same `❯` in the same column, in the box's own colour; a message opening with a markdown block marker renders as a paragraph, and one opening with a code fence starts the fence below the prompt line. *Why:* the standard is the user box, not either reference CLI — "if we are going to do the background thing for user messages in the chat, the input should be the same" — and pi's box hardcodes its blank row above and below, so the composer carries the same two.
   - A sent skill invocation is one ordinary user box containing `/skill:name` and its arguments, with only the command in `accent`; no separate skill card or instruction body, including under ctrl+o; the full instructions stay in model context and stored messages. No persistent composer label. *Why:* the owner wants the command they sent, not two transcript blocks for one input.
   - Queued steering and follow-up keep pi's pending location and queues but draw as shaded `❯` input blocks. One quiet `π` header per delivery group distinguishes next-response steering from after-task follow-up and counts multiple messages; messages retain separate blocks and a blank between them. The actual dequeue-key hint sits once on the first header, saying it edits all queued input; steering also names Ctrl+Enter to send now. Headers wrap at narrow widths. Pi's above-editor widget container supplies one unshaded blank after the last block before the working row/composer; the pending renderer adds none. No second queue or widget. *Why:* messages delivered together need one label, and a trailing hint crowded the message-to-composer gap.
   - Ctrl+Enter interrupts the root response, awaits cancellation, and sends native queued steering plus the expanded composer draft. Follow-ups stay queued for after the task; Enter, Option+Enter, Option+Up, shell mode, commands and dialog/fleet focus keep their meanings. Empty input does nothing. Work already done is not undone, and children are not blanket-cancelled. *Why:* a wrong-direction response should stop without manually restoring and resending input.
   - Tab opens nothing on a line that does not start with `/`, so `@path` is untouched, and offers only what a command declares, nothing where it declares none — chosen over an allowlist of completing commands, which would take pi's own `/model`, `/thinking` and `/login` off it. The menu also opens on the characters a path is typed with (the command's space, `/`, `~`), first line only; an accept shows the next level and stops.
   - `/add-dir` respects explicit paths literally: an addable slash-ended path comes first, children below, preserving relative, `~/…` and absolute spelling. Empty input starts at siblings; policy exclusions still apply. Tab accepting unchanged text closes the menu; accepting a different directory opens its level. *Why:* automatic descent selected the wrong directory; literal paths also remove the climbing heuristic.
   - Shell mode: a leading `!`/`!!` moves into a red (`error`) `!` prompt, with command text in `userMessageText` and the whole composer in subtle `toolErrorBg`. Backspace at command start exits the mode; `!!` keeps its context exclusion. Enter and Alt+Enter both execute. *Why:* the owner wants the mode in the prompt, not an extra character in the command; normal text keeps the tinted surface readable.
   - The shell block: the composer's red `!`, `userMessageText` and `toolErrorBg` carry into the transcript as soon as execution finishes, including mid-turn. One unshaded blank separates it from the output summary, which carries line count and outcome; it shows the last four lines (first two and last two on failure/cancellation), two in, with `… N more lines`, `▸`/`▾` for longer output and ctrl+o for all retained output, and states no output, cancellation and truncation explicitly. While running it keeps `Running <cmd>… 3s` without streaming output. `!` output enters context and starts one turn, after the agent would otherwise stop if busy; a cancelled `!` adds context without a turn; `!!` never enters context (`docs/pi-coupling.md`, The owned `!` block). *Why:* the owner wants a short readable result, not a dump or a completed command hidden behind the agent's turn.
   - The `!` command runs in zsh sourcing `~/.zshrc`, rc aliases included. *Why:* `!` exists to run what the user would type at their prompt, and an interactive shell without a tty prints prompt and job-control noise, so the rc is sourced into a non-interactive zsh.
6. **Fleet = Claude's subagent statusline shape, pi's glyphs.** `○ agent › title · tokens · model` per child under the status line, five rows then `↓ N more`; the title is the launch's own `title`, written by the launching model, else its shortened task; Down from the prompt's last line enters the rows, the highlighted row shows `❭`, Enter peeks the child's transcript, Esc or up returns. *Why:* the owner wants the Claude Code panel with its Enter peek and asked for pi-flavoured markers in place of `⏺`/`◯`; a task's opening words named the prompt, not the work, and the launching model writes the title in the call at no extra request, as Claude Code's Agent `description` does.
   - The peek is a rule 11 dialog mounted as plan approval and the questionnaire are — in the composer's slot, not a floating overlay — at a fixed half of the terminal's rows, the window padded to what the chrome leaves, so frame and composer hold still while the main transcript above and the fleet below say where the user is; a second slot dialog (question, plan approval, action confirm) closes it first. *Why:* a content-sized centred overlay re-centred on every row and, with the main thread bleeding round two rules, read as no border; a true switch is out (pi has no layout swap, pi-subagents no attach), and the place the other dialogs take is the depth cue the owner asked for.
   - Its transcript is the run's `events.jsonl` replayed in rule 2's grammar in full (tool rows with their `↳` summary, groups, handle, bodies under ctrl+o, assistant markdown, sent steers as rule 5 blocks), rule 4's `π` turn line per settled run, scrolling. The whole journal is read at open, session-restored runs included (their artifact directory is read back from the branch's subagent results); a run with no artifact directory known to this process (a foreground run) keeps pi-subagents' text tail. Not carried: a click on one sealed group (the dialog registers no click region); ctrl+o is the way. *Why:* the text tail named tools without outcomes, a second grammar drifts from the main thread the owner wants the child to read as, and a tail-only read left a late peek without the history it was opened for.
   - Below it, separated by a blank row, rule 3's working row above rule 5's composer with its two shaded rows, anchored across running and settled states, matching the main composer's accent prompt and sent-message markdown and colours; Enter steers the child, `/stop` sits behind a confirm, Esc goes back to the row it left. Native, unshaded slash completion offers only peek commands; action feedback appears only when needed; no permanent bottom shortcut strip. The compact `peek` header keeps identity (`agent › title · model · tokens`) and the terminal state word visible by shortening the title first, with `esc back` beside it. *Why:* the owner wants to look at and talk to a child as if it were the main thread — the same conversation surface, distinguished by its frame and identity rather than extra instructions.
7. **Stability over fidelity.** Build on a documented pi or plugin API. An undocumented export or heuristic is allowed only with a test that fails on the pin bump, plus an entry in the coupling inventory (`docs/pi-coupling.md`) unless repair-only, which carries only its pin; `stability.test.mjs` enforces the import and event side mechanically and pins the source text every heuristic assumes. *Why:* pi breaks extension APIs across 0.x releases; prose fails silently, tests fail loudly.
8. **Glyph at the edge, text two in.** A line that opens with a glyph (`•`, `π`, `❯`, `!`, `❭`, `▸`/`▾`) starts at column 0; a line without one (`↳`, a `!` command's output lines, the status line, the fleet rows) starts two columns in. A fold handle's caret takes the dot column, so it lines up with the `•` rows it owns. A leading heading renders bold on the bullet line instead of leaving the bullet on a line of its own. Every block has one blank line above it — each assistant text block, two in one message included, a row, a group, a completion or turn line, each queued input — and a group is one block, none inside; a row that draws nothing takes no line. Under ctrl+o a group's rows are blocks again: the handle sits on its first row and every later row, completions included, has its blank above; main thread and peek alike. *Why:* "even spacing for every row", and two replies in one message sat flush once the hidden reasoning took pi's spacer with it. pi's `outputPad` is 0 so its own lines (assistant text, the user box, "Operation aborted") share column 0; pi allows only 0 or 1 there. *Why:* "one inset" read as margins on the chat, the owner's reference has the rows at the edge and only the status block inset, and "glyph or not" needs no list. The lines that break it are pi's: assistant text sits at column 0 under its bullet, and pi's status and warning notices sit at column 1 whatever `outputPad` is; only patching pi reaches them — ruled out as cosmetic.
9. **Background = user messages (queued or sent), composer, the sent `!` command and a dialog's active tab.** The user box, composer and shell block share rule 5's shade; a dialog's active tab is the explicit exception (rule 11). No tool card (every plugin takes the row renderer) or activity summary has a background. pi's rare compaction and branch notices are pi's, and pi-subagents' own slash-command outputs (`/subagents`, `/prompt-workflow`, `/run`, …) are the plugin's. The shade encodes a reading: a shaded block is what the user typed, unshaded text at column 0 is what the assistant said, and two in is what a machine produced on the user's behalf (`↳` lines, a `!` command's output). *Why:* `bg_wait`'s green card was a third background and read as a different program; the owner wants the place they type to look like what they typed, and the shell block was the one typed thing that did not look typed.
10. **A pinned plugin earns a tool row, not a panel.** `web_search` (pi-web-search) uses `• Searched "query"`, joining rule 2's group on success; alone it has the answer's first line below. The owned `web_fetch` takes the same shape, `• Fetched host`. The `π` voice records workspace changes (`π Added … to the workspace`). The one panel above the composer is the working row (rule 3). *Why:* the todo plugin's panel above the composer was a second `○` meaning, and both reference CLIs dropped the surface it mirrored.
11. **A dialog is one frame, one cursor, one accent.** Every surface we draw that takes the keyboard follows this: plan approval and the questionnaire through `dialog.mjs`, the fleet peek on the same grid; pi's native `confirm`/`select` stay pi's (rule 7) until owned. *Why:* each dialog had collected exceptions under rules 2, 9 and 10 and drifted from rules 1 and 8; the accent discipline the owner liked in RPIV's questionnaire — one accent that always means "here" — needs none of its glyphs or boxes.
    - Frame and grid: top and bottom `borderAccent` rules, no side walls; `❭` at column 0 and everything else two in (rule 8). Nested content (a preview) is a `borderMuted` box centred in the free width, stacked when narrow.
    - Accent = focus (cursor, focused label, active tab on `userMessageBg`); bold = title, question and chosen, both when both; muted = descriptions and `↳ note:` lines; dim = hint and placeholder; success = answered inactive tab; warning = missing answer; answers plain.
    - Marks: single-select none, the chosen row ends ` ✔`; multi-select `[✔]` accent, `[ ]` muted. Text is typed inline through the borderless native editor behind a dim placeholder, never in an editor box. The fleet peek's composer is the exception: it takes rule 5's shade and `❯`, as it is a composer and its sent steers sit above it in the same shade.
    - Plan approval: title, vertical Yes/No, feedback beside No, no hint. Blank Enter or Esc stops without another model turn; Up from the first line or Tab returns to Yes keeping the draft. `submit_plan` retains the full plan and revision in tool-result details on the active branch; targeted edits assemble a new draft for the same approval flow. Pending and expanded rows show that exact snapshot, not patch arguments; a read shows as `Read plan` with its revision. `/plan show` opens a scrollable view without changing mode or asking the model. Restoring a plan never restores execution permission; compaction leaves the branch state recoverable with `action: read`. *Why:* localized feedback needs an edit, not model-generated replacement prose; keeping native snapshots avoids another plan store and repeated context injection.
    - Questionnaire: a single question has no header; tabs are padded cells, `☐`/`☑` for unanswered/answered question tabs and `✔ Submit` for the action tab, which keeps review-before-confirmation and missing-answer checks; no bracketed tabs, and narrow headers keep the active tab visible. Tab opens the note under its option; the free answer is typed, and kept literal, in its own last row, which carries the next option number (`N. Type something.`) during editing too — the number is presentation, never part of the answer. One blank below the header or top rule and above the one dim ` · `-joined hint; eight-row minimum; arrows move, PgUp/PgDn page.
12. **Use semantic theme colours, not literal palette values.** Accent means identity/focus; success/error/warning mean outcome or state; muted/dim carry hierarchy. Plan=warning and execute=success are local conventions, not Catppuccin requirements. Shell-red is rule 5's explicit mode exception; backgrounds remain confined to rule 9's surfaces. Raw SGR is only reset repair or cursor styling, not a second palette. *Why:* one semantic mapping survives the Latte/Mocha switch without recolouring already-consistent surfaces.
